# ADR-0001: mokumesh の土台 — 範囲・mokume との関係・受け渡し・形状・出力・操作

## 状態

採用 (2026-11-07) / 改訂あり (本文の「改訂 (日付)」見出し)

## 文脈

### 本番を有料の道具に頼っている

mokume は絵と動きを作る側の道具で、プロジェクションマッピングは本体の仕事にしていない ([mokume の ADR-0041](https://github.com/mokume-metal/mokume/blob/main/docs/decisions/0041-standard-scope-map.md) の基準 5)。これまでの想定は「mokume が Syphon で絵を出し、MadMapper が受けて映す」だった。しかし MadMapper は有料なので、作品を本番へ出すたびに、有料のソフトがあることが前提になる。

### 汎用のマッパーを作っても、得るものは少ない

Syphon を受けて歪めるだけの汎用のマッパーなら、無料のものも OSS のものも既にある。作る意味があるのは、mokume の作品を前提にしたときに得られるものがある場合で、具体的には次の 3 つである。

- 精度を落とさない受け渡し: mokume は作業空間を半精度で持っている (mokume の ADR-0011)。8 bit の受け渡しでは、その精度と EDR が失われる
- 面ごとに描くこと: 大きな 1 枚を切り抜くのではなく、映す面の形を作品が知ったうえで描く
- 較正の結果をテキストで持つこと: mokume の作品と同じように、差分を読めてバージョン管理できる

### mokume に既にある材料

- mokume の `mokume watch` は、子プロセスが焼いた絵を IOSurface の番号で受け取っている (mokume の ADR-0032 決定 3)。半精度のまま、面を複数枚まわし、書き終えた枚数を面の属性に載せる形である。プロセスをまたいで絵を渡す道は、mokume の上で既に動いている
- 外のパッケージは出力段の後ろの口 (`OutputFrame.texture`) から絵を受け取れる (mokume の ADR-0024)。mokume-syphon はこの道を通っている

## 決定

### 1. 範囲はマッピングだけ。作品の仕事は作品の側で書く

mokumesh がするのは、届いた絵を正しい場所へ正しい形で映すことだけである。

| する | しない (作品の側で書く) |
| --- | --- |
| 位置合わせ・幾何学的な変換 (2D と 3D) | 動画・画像の読み込みと再生 |
| マスク | シーンの切り替え・キュー・タイムライン |
| プロジェクタの重なりのブレンド | エフェクト・合成 |
| 複数のプロジェクタと表示装置の管理 | 音・照明の制御 |
| 較正の GUI とテスト用の模様 | — |

作品を切り替えたいなら、作品が自分でシーンを持つ。外から合図を送りたいなら、mokume の OSC・MIDI を使う。

**退けた案**: MadMapper と同じように、動画の再生やシーンの切り替えまで持つ。これを採ると、mokume が本体で避けた「専用の道具の仕事を劣った形で抱える」問題を、こちらで抱えることになる。しかも mokume の作品は、それらを自分で書ける。

**代償**: mokume 以外の素材 (動画ファイルなど) を映したいときは、それを再生するスケッチを書くか、Syphon で送る別のアプリを使う必要がある。

> 破れたとき: 「本番で便利だから」という理由で再生とキューが入り、マッピングの品質より周辺機能の保守に手が取られる。

### 2. mokume は mokumesh を知らない。mokumesh が mokume に追随する

- mokume 本体のコード・検査・CI は mokumesh に依存しない (mokume の ADR-0041 決定 2 の改訂 (2026-11-07))
- 本体の版への追随と、本体の変化で壊れたことへの気付きは、mokumesh の側が負う
- 送り手の部品 (決定 3) は、このリポジトリが外のパッケージ (別の product) として配る。部品は mokume の公開の口だけを使う。mokume の内部の取り決め (`mokume watch` と子の間の環境変数や区画のファイルなど) には依らない

**退けた案**: mokume-syphon と同じように、本体の CI で下流の検査をしてもらう。メンテナは「mokume は mokumesh を知らなくてよい」と決めた。本体の PR に追随の負担を移さない。

**代償**: 本体の変更で mokumesh が壊れても、気付くのはこちらの追随の時点になる。こちらの CI で、mokume の `main` に対して組む検査を定期的に回すことで補う (最初のコードを入れた後に起票する)。

### 3. 受け渡しは Syphon と専用の受け渡しの 2 系統

| | Syphon | 専用の受け渡し (いま) | 専用の受け渡し (mokume に汎用の口が入った後) |
| --- | --- | --- | --- |
| 役割 | 汎用の入口。mokume 以外のアプリの絵も、MadMapper へ渡す既存の道もこれで受ける | mokume の作品のための本線 | 同じ |
| 精度 | 8 bit | 8 bit (mokume の出口が渡す形式そのもの) | 線形の半精度も選べる |
| 余分なコピー | 送り手の側で 1 回 | 送り手の側で 1 回 (受け手の面へ blit する) | 無し (mokume の出力段が受け手の面へ直接書く) |
| 同期 | 暗黙 | 送り手の blit が終わった知らせ (`addCompletedHandler`) で FRAME を送る。CPU は待たない | 同じ |
| 面の渡し方 | 全域の IOSurface の番号 | **受け手が面を用意し**、mach port で渡す (番号の総当たりで他のプロセスから読まれない) | 同じ |
| 載せる情報 | 絵だけ | フレームの番号・送り手の時刻・送り手が受け取った瞬間と書き終えた瞬間の host time | 同じ |

専用の受け渡しの約束は、最初から次の形を前提に作る。

- **名前つきの複数の映像**: 送り手は「front」「left」のように名前を付けた複数の映像を出せる。最初の実装は 1 本だけである
- **受け手から送り手へ返す情報**: 面の大きさ・形・マスク、3D なら UV の配置を送り手へ返す。作品はそれを読んで、面に合わせて描ける。これは情報を渡すだけで、mokume にマッピングの仕組みを持たせることではない

**退けた案**:
- `mokume watch` の受け渡し (mokume の `Schemas/viewport-surface.schema.json`) を読む。半精度の道が既にあるのは魅力だが、`watch` から起こしたときにしか無く、配った `.app` では使えない。しかも本体の内部の取り決めに縛られ、決定 2 に反する
- Syphon だけにする。8 bit に落ち、名前つきの複数の映像と、送り返す情報を載せる場所が無い
- NDI や OMT のようなネットワークの規格。同じ Mac の上では、エンコードとデコードの分だけ遅れと負荷が増える。マッパーを別の Mac で動かす需要が出たときに比べ直す

**代償**: 受け渡しの約束と、送り手の部品の両方を保守する。半精度は 8 bit の 2 倍の帯域を食うので、精度を選ぶのは送り手の責任になる。

#### 改訂 (2026-11-07) — 精度・同期・面の渡し方を、実装で分かった事実に合わせる

採用した日のうちに、最初の実装 ([#5](https://github.com/mokume-metal/mokumesh/issues/5)) で 3 つの前提が崩れた。表は現行の形に直してあり、ここには何が変わったかと理由を残す。

- **精度: 当初は「8 bit・10 bit・半精度から送り手が選ぶ」と書いた。** mokume の出口が受け取れる `OutputFrame.texture` は `rgba8Unorm` (Display P3 の原色・sRGB の曲線・straight alpha) で、作業空間の半精度は公開の口に出ていない。決定 2 (公開の口だけを使う) の下では、送り手が選べる精度は 8 bit だけである。約束には形式の欄を残し、いまは `rgba8DisplayP3` だけを持つ
- **余分なコピー: 当初は「無し」と書いた。** `OutputFrame.texture` は `receive` から戻ると次のフレームで上書きされるので、送り手は受け手の面へ 1 回 blit するしかない。Syphon と同じ 1 回である
- **同期: 当初は `MTLSharedEvent` と書いた。** shared event をプロセスの外へ渡す公開の道は XPC だけで、XPC で知らない相手と出会うには、launchd に登録したサービスが要る。そこで送り手の blit の完了の知らせで FRAME を送る形にした。CPU は待たない。1280×720 で、送り手が絵を受け取ってから受け手に通が届くまでは中央値 0.10 ms だった (blit の GPU の時間を含む・2026-11-07 実測)
- **面の渡し方は、当初のとおり mach port で渡せた。** 受け手は `bootstrap_check_in` で名前を登録し、送り手は `bootstrap_look_up` で引く。launchd に宣言していない名前でも、署名の無いプロセスどうしで通った (2026-11-07・macOS 27 で実測)。面は**受け手が**用意する。mokume に「出口が渡し先の面を用意する口」が入ったとき、出力段が受け手の面へ直接書けるようにするためである
- **送り手が BYE を送らずに落ちたこと**は、mach の dead-name の知らせで知る。受け手のスレッドは 1 本の受け口で、通と知らせの両方を受ける
- **受け手が居なくなったことも、送り手は同じ知らせで知る** (2026-11-08 追記・[#10](https://github.com/mokume-metal/mokumesh/issues/10))。受け手が面を 3 枚とも握ったまま終わると、送り手には送るものが無く、送りの失敗では気付けない。知らせが無いと「面が返らない」と数えて名乗り直し、面の喪失と取り違える

**Syphon を上回るには、mokume 本体に汎用の出口の口が要る**とメンテナが判断した (2026-11-07)。どれも mokumesh 専用ではなく、mokume は mokumesh を知らないままでよい (決定 2)。

- 出口が渡し先の面を用意し、出力段がそこへ直接書く (コピーを 0 回にする) — [mokume#3850](https://github.com/mokume-metal/mokume/issues/3850)
- 出口が、作業空間の精度で絵を受けることを選べる — [mokume#3851](https://github.com/mokume-metal/mokume/issues/3851)
- 出口へ絵が届くまでの 1〜2 フレームを詰める — [mokume#3852](https://github.com/mokume-metal/mokume/issues/3852)

これらが入ったら、送り手の部品だけを差し替える。受け手は変えない。

退けた案:
- 名前の登録に `bootstrap_register` を使う。非推奨で、`bootstrap_check_in` が通るので要らない
- 全域の IOSurface の番号で渡す (Syphon・mokume の ADR-0032 と同じ)。mach port が通るので、他のプロセスから読まれる形を選ぶ理由が無い
- launchd に XPC のサービスを登録して `MTLSharedEvent` を渡す。アプリを .app に束ね、ログイン項目として人に承認してもらう手間が要る。完了の知らせで遅れが 0.1 ms 程度に収まっているので、見合わない。.app に束ねる段で比べ直す

代償:
- いまの専用の受け渡しは、効率では Syphon とほぼ同じである。1920×1080・60fps で実測すると (2026-11-07・[#7](https://github.com/mokume-metal/mokumesh/issues/7))、描いてから受け手に届くまでは中央値 17.8 ms と 19.7 ms で、専用のほうが 2 ms ほど早い。ただし同じ表示の刻みで提示すると差は消える (どちらも 44.5 ms)。送り手の GPU の時間は 1 枚あたり 0.16 ms と 0.11 ms で、Syphon のほうが短い。遅れの大半は、mokume が出口へ絵を渡すまでの 1〜2 フレーム (mokume#3852) と、提示の刻みである
- 勝っているのは、時刻・名前つきの映像・全域にしない面と、送り返す情報の置き場 (種類の番号だけを取ってあり、中身は面を返す段で決める) である

### 4. 時刻: 送り手は自由に回し、受け手は表示に合わせて最新の 1 枚を取る

- 送り手 (作品) は自分の周期で描く
- mokumesh は各表示装置の垂直同期で起き、その時点で書き終わっている最新の 1 枚を映す
- 1 枚ごとにフレームの番号と時刻を運ぶ。mokumesh は、届いた時刻と表示の時刻のずれを測って示せる

**退けた案**: mokumesh が表示のタイミングを送り手へ返し、作品がそれに合わせて 1 枚ずつ描く。カクつきと遅れは最小になるが、mokume 本体に「外から刻みを受ける口」が要る。実測で必要だと示されるまでは採らない。示されたときも、口を足すかどうかは mokume の側の判断である。

**代償**: 作品の周期とプロジェクタの更新周期が合わないと、ときどき同じ絵が 2 回出たり、1 枚飛んだりする。作品の周期をプロジェクタに合わせて設定すれば避けられる。

### 5. 2D と 3D の両方を扱う。作品はモデルの UV に描き、mokumesh は視点から描く

- **3D**: 立体物のモデルを読み、各プロジェクタの位置・向き・画角を較正する。mokumesh はプロジェクタごとに、その視点から見たモデルに作品の絵を貼って描く。較正は最初、手で点を合わせる形で行う (モデルの頂点と、プロジェクタの像の上の位置を 6 点以上対応づける)。カメラを使った自動の較正は後から足す
- **2D**: 4 点合わせ・メッシュ・マスク。**2D の面は平らなモデルとして扱う。** 2D と 3D で、変換の仕組みを 2 つ持たない
- **分担**: 作品は面 (モデルの UV の組) ごとの映像を描き、プロジェクタのことを一切知らない。mokumesh は絵の中身を一切知らない。映像の名前 (決定 3) は、モデルの材質 (UV の組) に対応させる
- **ブレンドは幾何から計算する**: モデルの各点を何台のプロジェクタが照らしているか、面に対してどの角度で当たっているかから、画素ごとの重みを出す。2D の縁を直線的にぼかす形は、平面の場合の特殊な例として含まれる
- モデルの形式は、mokume が読める 3D の形式に揃える。作品とマッパーで同じファイルを共有できるようにするためである

**退けた案**: 2D だけで始め、3D は別の仕組みとして後から足す。複雑な形へのマッピングは最初から要件にある。2D を平らなモデルとして扱えば、仕組みは 1 つで済む。

**代償**: 平面 1 枚に映すだけの使い方でも、内部ではモデルと視点の計算を通る。較正の GUI は 3D を扱える分だけ重くなる。

### 6. 出力は「表示装置 → 領域 (仮想のプロジェクタ)」の 2 段で持つ

- **表示装置**: Mac が認識している出力 1 本。各表示装置に、全画面の窓を 1 つ置く
- **領域**: 表示装置の中の矩形 1 つが、プロジェクタ 1 台に当たる。分配器を使わなければ、表示装置 1 本に領域が 1 つ。分配器を使えば、たとえば 5760×1080 の表示装置 1 本に、1920×1080 の領域が 3 つ並ぶ
- 較正・マスク・ブレンドは**領域ごと**に持つ。表示装置は、どの領域をどこに置くかだけを持つ

Apple Silicon は、チップごとに繋げられる外部の表示装置の数が限られる。分配器を同じ仕組みの中で扱えば、繋げる台数を超えて増やせる。

**退けた案**: 表示装置 1 本をプロジェクタ 1 台と決め打ちする。分配器を使う構成で、1 台ぶんの較正を 3 台に分けて扱えなくなる。

**代償**: 分配器を使わない構成でも、設定は 2 段になる。

### 7. 較正は GUI で行い、結果は JSON Schema つきのテキストに残す

- 較正は、プロジェクタの像を見ながら角や点を動かす作業なので、GUI で行う (SwiftUI と Metal)
- 結果 (モデル・プロジェクタ・領域・マスク・ブレンドの設定) は、差分の読めるテキストに残す。形式は JSON Schema で定める (mokume の `Schemas/` と同じ扱い)
- 本番は、設定のファイルを渡して GUI を出さずに起こせるようにする

**退けた案**: 設定をコードで書く (mokume のスケッチと同じ書き方)。較正は目で見ながら手で合わせる作業で、数値を書いて走らせ直す形では合わせきれない。逆に、GUI の中にだけ状態を持つ形は差分を読めず、バージョン管理もできない。

**代償**: GUI と、テキストの形式 (とその版の上げ方) の両方を保守する。

## 影響

- 最初の Feature は、送り手の部品と専用の受け口を 1 本ずつ作り、1 台のプロジェクタで 4 点合わせを 1 面動かすところまでにする。そこで遅れと精度を Syphon と並べて測り、決定 3・4 の前提を確かめる
- 決定 3 の約束 (名前つきの複数の映像・送り返す情報) と決定 7 のテキストの形式は、どちらもプロセスの外とやりとりする形式なので、形を決めた時点で JSON Schema か型の定義に落とす
- mokume 本体に口が要ると分かったら (決定 4 の刻みなど)、ここには書かずに mokume 側へ Issue を立てる
- このリポジトリの検査・ブランチ保護・mokume の `main` に対して組む定期の検査は、まだ無い。最初のコードの PR と、別の Issue で入れる
